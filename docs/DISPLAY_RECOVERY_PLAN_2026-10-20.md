# خطة استعادة عرض التعرف وتحسين استمراريته — 2026-10-20

## النتيجة الحالية وما أُنجز في مراجعة الخمس دقائق

- أوضح المالك بعد شرح المقصود أن **مربعات الألوان لم تظهر**. إجابة «ظهرت
  الألوان» السابقة كانت ملتبسة، ولا تصلح دليلاً على نجاح طبقة التعرف. التصحيح
  متوافق مع سجل 0.9.35: نشر واحد، وصفر Canvas، وصفر إرسال رسم مسجل.
- راجعت مسار الكاميرا، قبول العمق، عامل التحليل، النشر، انتهاء الصلاحية،
  تركيب الواجهة، وأدوات الاختبار. لا يوجد سبب مثبت بعد لعدم وصول الرسم.
- أُعيد تنفيذ **82 اختباراً في 8 مجموعات: صفر فشل/خطأ/تخطي**. الاختبارات
  الحالية تختبر المنطق الخالص، ولا تثبت استدعاء Android View.onDraw أو ظهور
  شيء على الشاشة. انتهى تشغيل Gradle بنجاح في 47 ثانية، ومهمة الاختبار نُفذت
  فعلاً؛ لم يكن البناء وحده هو النتيجة.
- Cursor نفذ مراجعة قراءة فقط لحالات الاختبار الناقصة، دون تعديل أو بناء أو
  تحكم بالهاتف. راجعت نتائجها: بعض الحالات مغطاة جزئياً، ولا نعد اختبار helper
  بديلاً لاختبار دورة View كاملة. لا ندّعي RED لاختبارات لم ننشئها بعد.
- لم تتغير شيفرة التطبيق أو APK أو الصلاحيات أو شروط STOP في هذه الجولة.
  لا يوجد اختبار هاتف جديد أو تدريب أو تحميل بيانات/أوزان. بوابة 811 اختباراً
  السابقة ليست إعادة اختبار شاملة اليوم؛ التشغيل الجديد المحدد هو 82 فقط.

## 2. التحسين الأول: إثبات مسار الرسم قبل تغيير النموذج

### التنفيذ المقترح

1. إضافة تشخيص صغير محدود الذاكرة يميز قبول العامل، رفض النشر عند UI، قبول
   View، دخول onDraw، الرفض قبل الرسم، انتهاء الصلاحية أثناء الرسم، وعدم
   وجود خلايا قابلة للرسم. لا نحوّل كل frame إلى سجل نصي.
2. تسجيل أسباب الرفض منفصلة: expired، stopped، tracking_lost، revision_changed،
   invalid_geometry، empty_paint. إذا تعذر معرفة السبب من العقد الحالي، نضيف
   قراءة قرار واحدة متسقة بدل تخمينه من استدعاءات متفرقة تتسابق فيما بينها.
3. أوقات من نفس الساعة المحلية: received→worker_end، worker_end→UI، UI→draw؛
   فصل YUV/Bitmap/prepare/invoke/decode/ground قدر الحاجة. تُفصل أول عينة عن
   العينات الدافئة، ويظهر n مع كل إحصاء؛ لا تسمية n=1 كتوزيع أداء موثوق.
4. اختبار رسم اصطناعي debug-only بلا كاميرا ولا نموذج: مربعات ثابتة بألوان
   معروفة ونص «اختبار رسم — ليس تحليلاً للمشهد». نوع بيانات منفصل لا تقبله
   دالة الدمج الأرضي. نمط الاختبار لا يبقى كقناع قديم فوق كاميرا حية.
5. استخدام invalidate/postInvalidateOnAnimation الموجودين، لا مكتبة رسم جديدة
   أو تفعيل software rendering أو Canvas.clear واسع على افتراض غير مثبت.
6. عند الحاجة لقياس إطار العرض، نعيد استخدام APIs Android الرسمية المتاحة؛
   لا نفرض 60Hz أو مهلة عرض مشتقة من جهاز آخر. callback ليس دليلاً على تقديم
   البكسلات فعلياً للمستخدم.

### الاختبارات أولاً

- نتيجة تصل بعمر 239.72ms ثم تدخل UI ثم draw قبل/بعد 250ms: أسباب وعدّادات
  واضحة، وصلاحية لا تبدأ مجدداً عند أي مرحلة.
- انتهاء قبل onDraw لا يحسب submitted_calls؛ انتهاء بعد drawRect يحسب إرسال
  أوامر الرسم لكنه لا يحسبها عينة Canvas حديثة. تجميع helpers لا يثبت View.
- ساعة متراجعة، identity مكررة/قديمة، stop قبل callback، فقد تتبع/عودة تتبع،
  تبدل revision، انقلاب 180 درجة، حجم صفر ثم صالح، ونتيجة بلا وسوم ملونة.
- قيود ذاكرة وعدّادات واضحة؛ حذف callbacks عند توقف جلسة؛ لا callback قديم
  يعيد نتيجة أو يمس جلسة أحدث.
- فحص الاصطناعي يثبت فقط توصيل الرسم، لا دقة النموذج أو اتجاه الكاميرا أو
  أمان الطريق. اختبار Android فعلي مطلوب لاحقاً؛ المشروع لا يحتوي حالياً
  اعتماد Robolectric أو حزمة androidTest كاملة مثبتة بمجرد تسمية runner.

### قبول التحسين

اختبارات RED فعلية قبل API/سلوك جديد ثم GREEN، مراجعة مستقلة، بوابة كاملة.
لاحقاً فقط: عينة اصطناعية مرئية واضحة وعينة حية مع سبب مفهوم لكل رفض، ثم
فحص توقف/انتهاء يعيد العرض فارغاً. لا نقبل زيادة TTL أو إظهار نتيجة قديمة
كبديل عن إصلاح زمن التحليل. التطبيق العادي وSTOP والأصوات لا تتغير هنا.

## 3. التحسين الثاني: فصل «ماذا أرى؟» عن «هل عندي قياس هندسي جديد؟»

### التصميم المقترح

- مالك كاميرا ARCore واحد وعامل تحليل محدود واحد؛ لا CameraX ثانية ولا قائمة
  انتظار غير محدودة. نفس النموذج المثبت، لا تبديل أوزان قبل قياس المشكلة.
- نتيجتان مختلفتان نوعياً: Semantic2DObservation لوسوم الصورة فقط، ونتيجة
  هندسية لا تُنتج إلا من زوج raw depth/confidence مقبول بالإجراءات الحالية.
  غياب العمق لا يمنع عرض توقع «حائط»، لكنه يمنع ادعاء المسافة أو الارتفاع.
- 2D يحمل timestamp/receipt/generation/نوع المصدر والوسوم، ولا يحمل مرجع
  أرضية أو قرار حركة. لا تمريره إلى SemanticGroundDiagnostic بطريق الخطأ.
- مراكز خلايا 2D تُحوّل مباشرة بإحداثيات SDK من VIEW إلى CPU IMAGE؛ لا إعادة
  استخدام إحداثيات عمق snapped قديمة أو افتراض نسب أبعاد متساوية. نعيد
  استخدام تصحيح الاتجاه والـletterbox القائمين مع اختبارات التحويل.
- كل frame يعالج RGB مرة واحدة كحد أقصى. صور SDK تُنسخ وتُغلق على خيط
  المالك قبل العامل. إن توفر قياس هندسي صالح من الإطار المقبول نفسه يُلحق
  كبيانات خام مستقلة العمر؛ وإلا تبقى الهندسة UNKNOWN، بلا نقاط محفوظة قديمة.
- لا نجمع ماسكاً من إطار مع عمق من إطار مختلف لمجرد قرب وقت وصولهما، ولا
  نقارن ساعة المستشعر بساعة النظام بطرح غير معرّف. عدم التطابق رفض صريح.
- تبدأ cadence التشخيصية بحد محافظ مشابه للحالي؛ قياس كلفة GL والتحضير
  والاستدلال والعرض يسبق زيادة المعدل أو تغيير دقة المدخل. سقف النموذج ليس
  FPS الكاميرا. لا إسقاط انتقائي لعينات البرد من تقرير الأداء.

### اختبارات القبول

1. RGB صالح + صفر عمق: توقعات 2D ممكنة، هندسة UNKNOWN بالكامل، صفر turn/CLEAR.
2. RGB صالح + نفس timestamp عمق يتكرر: لا دليل هندسي مستقل جديد، ولا ثبات
   مصطنع من إعادة الإسقاط. نفس رفض raw الحالي محفوظ.
3. عمق قديم/ناقص/ثقة ضعيفة/تباين أحجام/strides: لا دمج؛ أسباب قابلة للاختبار.
4. rotation/crop/letterbox والحدود الفاصلة: لا clamp لإحداثيات غير صالحة ولا
   رسم وسوم منطقة مختلفة. الماسك categorical وليس ثقة احتمالية.
5. عمل متأخر/stop/تغير هندسة: لا نشر، ولا تسرب صورة/Bitmap، ولا إعادة فتح كاميرا.
6. ضغط العامل: مهمة واحدة؛ الطلب المرفوض لا يكتسب image ولا يكدّس buffers.

قبول هذه المرحلة يثبت استمرار ملاحظة الصورة فقط، وليس تحسن دقة الحوائط أو
التوجيه. مرجع الأرضية ما زال يتطلب دعم المنطقة والامتداد والهندسة والثبات؛
لا تخفيض حد الست نقاط أو استثناء الفرشة بمجرد وسم rug.

## 5. الخيارات الجاهزة وترتيب التأجيل

- الآن: إعادة استخدام Android View/Choreographer وARCore transforms والعامل
  والنموذج وYUV converter والاختبارات الموجودة. لا حزم مدفوعة أو مكتبات ضخمة.
- بياناتنا العامة الحالية Hypersim: مفيدة لفحص معادلات الإحداثيات، لكنها
  تحتوي حالياً geometry/labels دون RGB في fixture؛ لا تصلح وحدها لاختبار
  الاستدلال البصري ولا يصح تسميتها تدريباً. عند توسيعها لاحقاً نضيف RGB
  مختاراً فقط مع split ثابت ومصدر/ترخيص وhash وميزانية تنزيل واضحة.
- ADE20K العام: خط مقارنة منفصل، لا يعوض اختبار Redmi أو ارتفاع سجادة. لا
  نخلط معرفات NYU40 وADE20K. القياس السابق لم يصبح دقة ملاحة بمجرد وجوده.
- تبديل النموذج/إعادة التدريب: مؤجل حتى نميز إخفاق التشغيل عن خطأ التوقع،
  ونضع مشاهد held-out وحالة مقارنة متحكم بها وحقوق وزن/بيانات واضحة.
- حساس/سحابة/شراء: آخر الخيارات، لا حاجة مثبتة الآن، ولا دفع/رفع صور/صلاحيات
  جديدة دون موافقة مستقلة. لا إضافة Internet في هذه المرحلة.

## 6. ترتيب التنفيذ والتحقق والتراجع

أولاً عقد/اختبارات تشخيص الرسم → RED/GREEN → دمج ومراجعة → بوابة كاملة.
ثانياً فصل 2D بعد ثبوت القياس → اختبارات ندرة/تكرار العمق → دمج ومراجعة →
بوابة كاملة. نحتفظ بكل تحسن كوحدة Git قابلة للرجوع عنها دون لمس عمل المالك.
لا تثبيت نسخة جديدة أو تجربة كاميرا أثناء انشغال المالك بانتظار البناء.

بوابة الهاتف التالية بعد الكود الجاهز: شرح بصري واضح لمعنى المربعات، ثم
رسم اصطناعي منفصل، ثم 20 ثانية للمشهد نفسه بإضاءة وأرضية ظاهرة مع تأكيد
جديد للاستعداد. لا مشي، ولا طلبات متكررة غير مجهزة، ولا اعتبار speak result=0
دليلاً على سماع صحيح. عند فشل أي بوابة نسجل السبب ونوقف التقدم لا نخففه.

## مصادر أولية راجعتها في هذه الجولة

- [Google ARCore Raw Depth](https://developers.google.com/ar/develop/java/depth/raw-depth):
  تكرار depth timestamp قد يكون إعادة إسقاط، وليس قياس عمق جديداً.
- [Android Choreographer](https://developer.android.com/reference/android/view/Choreographer):
  توقيت رسم View مرتبط بإطارات العرض؛ نجاح النشر لا يعني رسماً فورياً.
- [Android hardware drawing](https://developer.android.com/develop/ui/views/graphics/hardware-accel):
  invalidate يحدث display list؛ الاستدلال وحده لا يثبت onDraw أو تقديم البكسلات.

الاقتباسات أعلاه استنتاجات تصميمية من العقود الرسمية، وليست إثباتاً لسبب
فشل Redmi. مصادر المكتبات/الأوزان والبيانات تراجع منفصلة عند أي دمج جديد.
