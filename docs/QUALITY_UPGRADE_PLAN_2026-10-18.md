# Quality upgrade program — phone-first TriGuide

Codex owns requirements, safety contracts, and review; Cursor implements one scoped slice at a time and reports test evidence in `docs/BRIDGE_TO_GPT.md`. This is a development plan, not a claim that the app currently provides reliable mobility guidance.

## Measured priorities

1. **Audio delivery, now:** Preserve the verified hazard-episode scheduling, but make Android TTS select an actual installed offline `Voice`, not just call `setLanguage` after checking that some offline voice exists. The current `AndroidVoiceSpeaker` can otherwise select a different engine voice. Use `getVoices` → filter `!isNetworkConnectionRequired` → choose by intended language and a deterministic quality/latency policy → `setVoice`, with text-only failure if no offline voice can be selected. Android documents these APIs and quality/latency metadata: [TextToSpeech](https://developer.android.com/reference/android/speech/tts/TextToSpeech), [Voice](https://developer.android.com/reference/android/speech/tts/Voice). Unit-test ranking and fallback, then confirm the actual Redmi sound later. Do not claim perceived voice quality from API metadata alone.
2. **Decision architecture, next:** Keep the existing detector-only `UNKNOWN`/`HOLD` contract. Move camera evidence adaptation and temporal scene state out of Compose's 50 ms loop behind a testable interface. Timestamp, validity, freshness, and source must survive into guidance; missing/stale frames stop the virtual command. Do not authorize a straight path or side turn based on absent boxes. Keep synthetic-world evidence separate. This is R1 in `docs/ROOT_ARCHITECTURE_REDESIGN.md`.

   Concrete review finding: `AssistCameraDrive` currently calls `SceneObservations.fromCamera` and `GuidanceSession.onCamera` every 50 ms, while the measured detector ran about 7–9 results/s. `TemporalDecisionSmoother` counts calls (`CONFIRM_FRAMES = 3`), not distinct inference results. Today detector-only camera decisions are `HOLD`/`UNKNOWN`, so this is not a demonstrated unsafe turn; it would become a false three-frame confirmation if future walkable-area decisions used the same loop. R1 must ensure temporal votes count **unique timestamped samples**, not replayed loop ticks, and that a stale sample immediately causes `UNKNOWN`/zero virtual command. Unit tests should replay the same result many times, then advance three distinct results, then age the frame past the stale threshold.
3. **Vision evaluation before model swap:** Assemble a small consented, labeled set of indoor clips from the actual Redmi, including an empty-looking corridor, a table mistaken for `toilet`, packaging mistaken for `person`, shiny/dark floors, doors, stairs, and moving people. Measure inference FPS, latency, battery/heat, false walkable regions, missed obstacles, and label confusion against the current baseline. Only then compare legally usable lightweight walkable-area segmentation models on-device. Google's [MediaPipe Image Segmenter Android guide](https://ai.google.dev/edge/mediapipe/solutions/vision/image_segmenter/android) supports category/confidence masks and live-stream callbacks, but supplies an API, not a validated indoor-walkability model.
4. **Optional geometry, later:** Explore depth as a separate device capability only after camera-session compatibility is demonstrated. [ARCore Depth](https://developers.google.com/ar/develop/depth) is motion-dependent and most accurate around 0.5–5 m; depth is not itself evidence that a surface is walkable. Never require it for the phone-only fallback.
5. **Scene intelligence, after evidence:** A human-like on-demand description can summarize supported observations with explicit uncertainty. Junction questions/left-right alternatives need persistent walkable-region evidence; a generic vision-language model's fluent prose must not drive the safety policy or claim a safe route without validation.

## Acceptance rule for every slice

Record source diff, focused tests, full app tests/build, and an honest phone verification state. Preserve `HOLD`/`UNKNOWN` when positive evidence is missing, keep safety disclosures and on-demand Describe separate from automatic guidance, and do not change hardware/cloud scope or add a network/API-key dependency. Do not turn research papers, model cards, repository popularity, or static screenshots into real-world safety claims.
